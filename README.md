## Введение

Bakery Management System — клиент-серверное приложение для управления основными бизнес-процессами пекарни, включая работу с товарами, складом, пользователями и продажами.

Проект был реализован в рамках учебного задания, однако переработан в полноценную архитектурно разделённую систему с выделенным backend на C++ и отдельным клиентским приложением на Electron. Основной акцент сделан на разработке серверной части, отвечающей за бизнес-логику, работу с базой данных и предоставление REST API.

Система построена по принципу разделения ответственности: frontend выполняет роль интерфейса и взаимодействует с backend через HTTP-запросы, в то время как вся логика обработки данных сосредоточена на стороне сервера.

- JWT-аутентификация с хранением идентификатора пользователя и роли
- Поддержка ролей: `user`, `seller`, `admin`
- Разграничение доступа к функциональности в зависимости от роли
- Просмотр информации о текущем пользователе
- Управление пользователями (администратор)

### Управление товарами
- Создание и управление карточками товаров
- Загрузка изображений товаров
- Просмотр списка товаров с сокращённой информацией
- Просмотр детальной информации о товаре
- Удаление товаров
- Управление количеством товаров на складе
- Автоматический пересчёт затрат сырья при создании или обновлении товара

### Склад (Warehouse)
- Учёт складских позиций (сырьё и материалы)
- Пополнение складских запасов
- Списание сырья
- Просмотр текущих остатков
- Отслеживание даты последнего пополнения

### Корзина и оформление продаж
- Добавление товаров в корзину
- Изменение количества товаров в корзине
- Удаление товаров из корзины
- Просмотр содержимого корзины

- Оформление продажи через заказ (`/orders`)
- Разделение логики продаж по ролям:
  - **user**: оформление покупки с привязкой к пользователю (имя, email и т.д.)
  - **seller**: оформление офлайн-продажи без привязки к конкретному пользователю
- Автоматическое списание товаров при оформлении продажи
- Сохранение информации о продажах в системе

### Панель управления (Dashboard)
- Получение сводной информации о системе
- Последние действия:
  - продажи
  - пополнения склада
  - добавление пользователей

### Справочники (Dictionaries)
- Управление ролями и справочными сущностями
- Добавление и удаление производителей

## Архитектура

Система построена по модели клиент-серверного приложения с разделением frontend и backend.

### Общая схема

Frontend (Electron) → REST API → C++ Backend → MS SQL Server

### Frontend

Клиентская часть реализована на Electron и взаимодействует с сервером через HTTP-запросы.

Для работы с API используется единый модуль (`api.js`), который:
- инкапсулирует все запросы к backend
- добавляет JWT-токен в заголовки `Authorization`
- централизованно обрабатывает ошибки
- предоставляет единый base URL (`http://localhost:8080`)

### Backend

Backend реализован на C++ с использованием Crow framework и представляет собой монолитное серверное приложение.

Он отвечает за:
- бизнес-логику системы
- обработку HTTP-запросов
- работу с базой данных
- аутентификацию и авторизацию пользователей

### Архитектурный стиль

Backend построен по слоистой архитектуре:

Controller → Service → Data Access Layer (SQL Queries)

- Controllers: принимают HTTP-запросы и выполняют базовую валидацию
- Services: содержат бизнес-логику
- Queries layer: отвечает за взаимодействие с базой данных

### База данных

Используется Microsoft SQL Server.

Подключение реализовано через ODBC драйвер.
Все SQL-запросы инкапсулированы в отдельном слое `queries`.

### Аутентификация и безопасность

Система использует JWT-аутентификацию.

- В токене хранится:
  - `userId`
  - `roleId`

- Авторизация проверяется на уровне контроллеров через middleware-логику (`fromRequest`)
- Поддерживаются роли:
  - `user`
  - `seller`
  - `admin`

Пароли пользователей хэшируются с использованием PBKDF2 (SHA-256).

### Поток обработки запроса

Типичный запрос проходит следующие этапы:

Frontend → HTTP request → Controller → Service → SQL Queries → Database → Response → Frontend

Контроллер выполняет:
- извлечение и проверку JWT
- базовую валидацию
- передачу данных в сервисный слой

## Особенности реализации

### Управление данными

- Используется подход **soft delete**: записи не удаляются физически из базы данных, а помечаются как удалённые (`is_deleted`), что позволяет сохранять историю и избегать потери данных.
- Уникальность сущностей (например, email пользователя или название товара) обеспечивается с учётом soft delete: ограничения действуют только для активных записей.

### Аутентификация и авторизация

- Используется **JWT-аутентификация**, в токене хранятся `userId` и `role`, что позволяет выполнять авторизацию без дополнительных запросов к базе данных.
- Проверка токена выполняется централизованно через утилиты, с последующим использованием контекста пользователя в контроллерах.
- Реализована ролевая модель (`user`, `seller`, `admin`) с разграничением доступа к операциям.

### Обработка ошибок

- Реализована единая система обработки ошибок с использованием HTTP-статусов и кодов ошибок (например: `VALIDATION_ERROR`, `CONFLICT`, `ENTITY_NOT_FOUND` и др.).
- Бизнес-ошибки (например, дублирование email или недостаток товара) обрабатываются явно и возвращаются как соответствующие HTTP-ответы.
- Неожиданные ошибки (например, ошибки драйвера БД) логируются и возвращаются как `500 Internal Error`.

### Валидация данных

- Выполняется базовая валидация входных данных (проверка на пустые значения и корректность формата).
- Более строгая валидация (например, ограничения длины или диапазонов) частично отсутствует и может быть расширена.

### Работа с базой данных

- Используется **ODBC** для взаимодействия с Microsoft SQL Server.
- Реализована работа через слой запросов (`queries`), что отделяет бизнес-логику от SQL.
- Используются **транзакции** для операций, затрагивающих несколько сущностей (например, оформление заказа и списание ресурсов).

### Бизнес-логика

- Связь между товарами и складом реализована на уровне логики:
  - при создании или обновлении товара происходит списание соответствующего сырья со склада;
  - при продаже — уменьшается количество товаров и проверяется доступность ресурсов.
- Различаются сценарии продаж:
  - `user` — онлайн-покупка с привязкой к пользователю;
  - `seller` — офлайн-продажа без привязки к клиенту.

### Работа с файлами

- Изображения товаров загружаются через API и сохраняются локально на сервере.
- В базе данных хранится путь к файлу, который затем используется клиентом.

### Конфигурация

- Конфигурация приложения вынесена в переменные окружения (`.env`):
  - строка подключения к базе данных;
  - секрет для подписи JWT.

### Логирование

- Используются базовые логи:
  - ошибки проверки JWT;
  - ошибки драйвера базы данных (ODBC);
- Логи выводятся в консоль сервера.

### Сетевое взаимодействие

- Backend реализован как stateless-сервис (состояние не хранится в памяти между запросами).
- Поддерживается CORS для взаимодействия клиента и сервера при раздельном запуске.
- Сервер запускается в многопоточном режиме с использованием возможностей Crow.

## Установка

### 1. Клонирование репозитория

```
git clone --recursive https://github.com/Timofey10012/bakery-management
```
```
cd bakery-management
```

Флаг --recursive нужен для загрузки vcpkg (подключён как submodule).

### 2. Backend (C++)

Требования:
- CMake 3.20+
- MSVC (C++20 compiler)
- Git
- vcpkg (подключён как submodule)

Примечание: для сборки backend рекомендуется использовать
x64 Native Tools Command Prompt for Visual Studio (MSVC toolchain).

Инициализация vcpkg (из корня проекта):

```
cd vcpkg
bootstrap-vcpkg.bat
cd ..
```

Сборка (из корня проекта):

```
cmake --preset default
```
```
cmake --build build
```

Запуск:

```
build\bakery-backend.exe
```

Сервер запускается на http://localhost:8080.

### 3. База данных (MSSQL)

Выполнить файл db/init.sql через SQL Server Management Studio
или другой клиент MSSQL.

После инициализации доступен тестовый пользователь:
- Email: admin@bakery.local
- Пароль: admin123

### 4. Frontend (Electron)

Требования:
- Node.js LTS
- npm

Установка и запуск (из корня проекта):

```
cd frontend
```
```
npm install
```
```
npm start
```

### 5. Конфигурация окружения

Установить переменные окружения (глобально или в сессии):
- DB_CONNECTION_STRING — строка подключения к базе данных
- JWT_SECRET — секрет для подписи JWT

Пример строки подключения есть в .env.example.

### 6. Запуск проекта

После запуска backend и frontend:
- Backend: http://localhost:8080
- Frontend: Electron-приложение, автоматически взаимодействует
  с backend через REST API

Проект рассчитан на локальный запуск. HTTPS и деплой не настроены.
Вся коммуникация происходит через HTTP + JWT.

## Использование

Приложение представляет собой клиент-серверную систему с Electron-интерфейсом, взаимодействующим с backend через REST API.

После запуска системы весь функционал доступен через графический интерфейс приложения.

---

### Аутентификация

Пользователь проходит авторизацию через экран входа:

- регистрация нового аккаунта
- вход по email и паролю
- получение JWT-токена

После авторизации пользователь попадает в основное приложение. Доступ к функциональности зависит от роли пользователя.

---

### Роли системы

Система поддерживает три роли:

- **user** — клиент (покупки товаров)
- **seller** — продавец (офлайн-операции + работа со складом)
- **admin** — администратор системы

Роли определяют доступные действия и разделы интерфейса.

---

### Работа пользователя (user)

Основной сценарий:

- просмотр товаров
- просмотр карточки товара
- добавление товаров в корзину
- изменение количества в корзине
- оформление заказа

После оформления заказа:
- товары списываются со склада
- создаётся запись о продаже
- корзина очищается

---

### Работа продавца (seller)

Продавец использует тот же интерфейс корзины, но:

- оформляет офлайн-продажи без привязки к пользователю
- имеет доступ к операциям со складом:
  - пополнение сырья
  - списание сырья

---

### Администрирование (admin)

Администратор имеет полный доступ:

- управление пользователями
- управление товарами
- управление складом
- просмотр продаж
- доступ к dashboard

---

### Справочники (dictionaries)

Служебные данные для работы интерфейса:

- роли пользователей
- единицы измерения (UOM)
- производители

Используются в UI (в основном в выпадающих списках) и не требуют прямого взаимодействия пользователя.

---

### Dashboard

Главная панель отображает:

- последние продажи
- последние пополнения склада
- последние добавленные пользователи

## Ограничения и будущие улучшения

Проект реализован как учебно-пет-проект с акцентом на архитектуру backend-системы, поэтому содержит ряд упрощений и ограничений по сравнению с production-решением.

### Архитектурные ограничения
- Приложение работает только в локальном окружении (HTTP, без HTTPS)
- Отсутствует деплой и production-конфигурация
- Нет разделения на микросервисы — система реализована как монолитный backend
- База данных используется локально, без облачной или распределённой инфраструктуры
- Справочники (UOM и др.) не управляются через UI и требуют ручного добавления в БД

### Безопасность и авторизация
- Используется статическая соль для хэширования паролей (упрощённая реализация)
- Отсутствует механизм refresh-токенов и инвалидации JWT при logout
- Не реализована HTTPS-защита соединения
- Восстановление пароля и подтверждение email отсутствуют

### Бизнес-логика и модель данных
- Нет ручного списания или корректировки товаров (списание происходит только через операции покупки)
- Отсутствует моделирование порчи, возвратов и других складских событий
- Цена и итоговая сумма не отображаются в корзине (рассчитываются на этапе оформления заказа)
- Возможна ситуация добавления в корзину количества, превышающего доступное (проверка выполняется на этапе оформления заказа)
- Продажи не архивируются и не очищаются автоматически

### Клиентская часть (Electron)
- Отсутствует оффлайн-режим работы
- Упрощённая обработка ошибок (отображение только текстового сообщения)
- Минимальная UX-логика (нет полноценных лоадеров и fallback-состояний)
- Отсутствуют дефолтные состояния UI для части компонентов

### Хранение и данные
- Несоответствие названий между БД и API контрактом (контракт является источником истины для взаимодействия)
- Отсутствует автоматическая миграция схемы базы данных

### Возможные улучшения
- Добавление HTTPS и production-конфигурации
- Внедрение refresh-token механизма и управления сессиями
- Расширение складской модели (возвраты, порча товара)
- UI-управление справочниками (UOM, роли и т.д.)
- Добавление полноценного UX слоя (лоадеры, состояния загрузки, fallback UI)
- Улучшение модели корзины (динамический пересчёт суммы)
- Введение миграций БД и автоматической синхронизации схемы
